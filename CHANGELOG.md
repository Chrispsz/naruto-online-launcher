- **Optimize (Caretaker cycle 78)**: fixed an O(N × M) → O(N + M) complexity issue in `src/profiles/store.js`'s `getLaunchTimeline()` function. The function aggregates the launch log (capped at `MAX_LAUNCH_LOG_ENTRIES = 5000` entries) into per-day buckets for the manager UI's 7-day activity chart (called via the `profile:launch-timeline` IPC handler). The original implementation ran `_profiles.find(function (x) { return x.id === entry.id; })` INSIDE the `_launchLog.forEach` loop — a fresh linear scan + a fresh closure allocation per launch-log entry. Since both `_launchLog` and `_profiles` are scanned once per call, the inner scan made the function O(launchLog × profiles). The worst case (5000 entries × 50 profiles) was ~250,000 iterations of the inner `find` callback per call, with ~12.75M iterations across a typical session's chart refreshes. The fix pre-builds a `Map<profileId, profile>` once at the start of the function (O(_profiles.length) — typically <50 items, trivially cheap), then replaces each inner `_profiles.find()` with an O(1) `profileById.get(entry.id)`. This drops the aggregation to O(_launchLog.length + _profiles.length) and eliminates the per-entry closure allocation entirely (5000 closures/call → 0). Measured speedup at the worst-case input (5000 entries × 50 profiles × 30 days, 100 iterations): original 2.10ms/call → new 1.56ms/call — a 1.34× wall-clock reduction. Profiling shows `_profiles.find` was ~52% of the total runtime (1.09ms/call); the remaining ~48% is `_formatDate()` (called 5000×/call) + `forEach` overhead, which is unchanged. The optimization is purely computational — the produced `buckets` array is byte-for-byte identical to the original (verified by a 12-case standalone test at `/home/z/my-project/scripts/test-shinobi-launch-timeline.js` covering: empty launch log + empty/3 profiles, single entry today, multiple entries same profile same day, entries across 3 days + 2 profiles, entry for deleted profile, entry outside days window, days=1 single bucket, days=30 wide window, bursty traffic (105 entries × 5 profiles × 7 days), stress (5000 entries × 50 profiles × 30 days), mixed valid + deleted entries). For the typical user (50-200 launch log entries, 5-10 profiles), the impact is invisible (<0.1ms either way) — the value is defensive: removes the latent O(N²) shape that would matter if the launch log cap is ever raised or if a future change increases profile count. No protected i18n data, config field keys (incl. `forceBatata`), or existing test assertions touched. Lint stays at 0 errors, 0 warnings.

- **Optimize (Caretaker cycle 74)**: fixed an O(n²) `JSON.stringify` regression in `src/profiles/partition.js`'s `_persistSnapshots()` function. The cookie-snapshot persistence path enforces a 512KB cap on the on-disk `cookie-snapshots.json` file (profiles' auth cookies are snapshotted on window-close in low-spec mode to avoid the 30-80MB per-profile partition disk cost). When the cap was exceeded, the original code ran a `while` loop that called `JSON.stringify(_snapshots)` on the entire snapshots object on every iteration — once per dropped profile. For a degenerate case with 50+ profiles, this would have meant ~50 full re-stringifies of a ~500KB object (~25MB of redundant serialization work per save). The fix drops entries in a single pass using a running byte estimate (each profile's cookies array is independently stringify-able, ~1-6KB each), then re-stringifies at most TWICE total: once after the batch drop, once after the optional largest-entry fallback. The fallback path was also tightened: it now triggers only when the post-batch-drop json is still over the 512KB cap (the original code's `dropCount === 0` guard was a bug — it would not trigger when the loop had dropped some entries but a single huge entry remained). Added a `truncated N oldest` / `truncated N oldest + 1 largest` info log to surface the drop count for diagnostics. Behavior is otherwise identical: same cap, same oldest-first drop order, same 80% target threshold. Verified via a 24-assertion standalone test covering: small payload (no drops), over-limit with many similar-sized entries (oldest dropped, no fallback), huge-first (main loop drops it, no fallback), tiny-first-then-massive (loop drops tiny, fallback drops massive), empty, and single-entry cases. Test saved to `/home/z/my-project/scripts/test-partition-truncation.js` for future regression coverage. For the typical user (4-10 profiles, ~5KB each), the cap is rarely hit and the optimization is a no-op; the win is purely defensive against the degenerate case. Lint stays at 0 errors, 0 warnings.
