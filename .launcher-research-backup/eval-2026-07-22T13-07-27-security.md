## Nota: 4 / 10
O projeto tem fundamentos funcionais, mas falha criticamente em hardening do Electron, validação de entrada, isolamento de contexto e gestão de segredos. Várias decisões "pragmáticas" (webSecurity:false, nodeIntegration:true no manager, CSP permissivo, execução de comandos shell sem sanitização) criam superfície de ataque real. A criptografia do vault é bem implementada (AES-256-GCM + PBKDF2), mas a chave de máquina é derivável localmente sem segredo externo. IPC expõe handlers perigosos sem validação de origem. Não há assinatura de código, pinning de dependências ou SBOM.

## TOP 3 Quick Wins

1. **Ativar `contextIsolation: true` e `nodeIntegration: false` no ManagerWindow** (`src/ui/manager/ManagerWindow.js:28-30`) + mover `require('electron')` do `ui/app.js` para preload via `contextBridge`. Elimina RCE via XSS no dashboard.
2. **Remover `webSecurity: false` e `allowRunningInsecureContent: true`** (`src/app/Launcher.js:68-69`). Substituir por CSP restritivo + `webRequest.onHeadersReceived` para upgrade de Mixed Content. Mantém isolamento de origem.
3. **Sanitizar PID em `CpuOptimizer.js`** — validar `Number.isInteger(pid) && pid > 0 && pid < 2**31` antes de passar a `execFile`/`PowerShell`. Evita command injection se PID vier de fonte não confiável (ex: IPC malicioso).

## Risks Técnicos

- **Supply Chain**: `package.json` não tem `lockfileVersion` visível, mas `electron-log` e dependências nativas não têm pinning de integridade (hashes). Adicionar `npm audit` no CI + `package-lock.json` commitado + `integrity` no `package.json` (npm 7+).
- **Auto-update ausente**: Electron 11 (EOL dez/2021) não recebe patches de segurança do Chromium 87. Qualquer CVE no V8/Blink (ex: CVE-2022-3075, CVE-2023-2033) afeta o launcher. Planejar migração para Electron 28+ com Flash via Ruffle/WASM ou manter Electron 11 apenas em ambiente controlado (AppImage assinado, sem auto-update).
- **IPC sem validação de origem**: `ipcMain.handle` em `IpcRouter.js` aceita qualquer `profileId` string sem verificar se pertence ao usuário logado. Um renderer comprometido pode enumerar/deletar perfis alheios via `profile:delete`, `vault:set`, `inspector:enable`. Adicionar `senderFrame` check ou token de sessão por janela.
- **Diagnostics exporta logs sem rate-limit**: `diagnostics:export` pode ser chamado repetidamente para DoS de disco (zip de 5-10MB cada). Adicionar throttle (1x/5min) e limitar tamanho total.
- **Flash PPAPI binário não verificado**: `findFlashPlugin()` aceita qualquer binário >1MB sem verificação de assinatura/hash. Um atacante com write no `userData/flash-cache/` ou `resources/flash/` substitui o plugin por versão maliciosa. Adicionar hash SHA-256 conhecido no `manifest.json` e validar no boot.
- **JWT `oas_user` injetado via `session.cookies.set` sem `httpOnly: true`** (`src/network/api-login.js:38`). Cookie acessível via `document.cookie` no renderer — vazamento se houver XSS no jogo. Definir `httpOnly: true` (Flash PPAPI não lê JS cookies, o servidor valida via header).
- **`preload.js` expõe `__SHINOBI_DEBUG__` como objeto** — correto para Electron 11, mas `narutoLauncher.isDebug()` vaza flag de debug para renderer. Remover em build de produção ou guardar atrás de `contextBridge` condicional.

## Veredito

**Não está pronto para produção** sem as correções críticas acima (itens 1-2). O projeto funciona como "local tool" para usuário único confiável, mas falha em:

- Isolamento de contexto (RCE via XSS no manager)
- Hardening do Electron (webSecurity, CSP, nodeIntegration)
- Validação de entrada em IPC e execução de comandos
- Gestão de segredos (chave de máquina derivável, cookies não httpOnly)
- Supply chain (sem pinning, Electron EOL)

**Mínimo para release**: corrigir #1, #2, #3, #4 da tabela acima + adicionar validação de `senderFrame` nos handlers IPC sensíveis + pinning de dependências + documentar que Electron 11 é EOL e requer ambiente controlado.
